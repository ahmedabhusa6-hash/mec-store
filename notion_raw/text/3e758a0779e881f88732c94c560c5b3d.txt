Authority

Prompt Working Reference Boundary
The project uses a controlled  Prompt Working Reference  for active Prompt text and draft evolution.
- Claude  is the direct editor of Prompt Working Reference content.
- ChatGPT  reads, audits, tests, and records findings; it does not directly rewrite that Prompt Working Reference.
- Prompt Working Reference changes are  working draft changes , not approval or Canonical promotion.
- User approval remains mandatory  for promotion to Approved/Canonical.
- Neither agent may modify Canonical authority, approval status, promotion gates, or governance rules through the Prompt Working Reference.
- When a proposed Prompt change affects governance, authority, ownership, permissions, lifecycle, or promotion rules, it is  Governance-Touching  and requires a user decision.
The Prompt Working Reference must never be confused with the protected Canonical Registry state.
Core invariants
Review ≠ Authority
Draft ≠ Approved
Proposal ≠ Decision
Workspace ≠ Canonical Registry
There may be  zero or one Approved Prompt version  at any time; there must never be more than one. Until the first approval, the Approved state remains empty.
Version lifecycle
Draft → Candidate → Review → Revision → User Decision → Approved → Superseded
Rejected versions remain recorded and are never silently deleted.
Promotion gate
A Candidate may be promoted only when:
- Its Parent Version ID matches the current Approved Version ID.
- Required review and tests are recorded.
- Any Governance-Touching change has received the required user decision.
- The user explicitly approves promotion.
If the Parent Version ID is stale, promotion is blocked and the Candidate must be rebased.
Conflict rule
Two Candidates from the same Parent remain separate sibling versions.
They are not auto-merged.
A synthesis version may be created only as a new version that explicitly records which changes came from which parents/candidates.
Change classification
- Existing Project Rule
- Evidence-Based Repair
- Proposed Governance Decision
Synchronization rule
The transport between ChatGPT and Claude may be manual or automated in the future. The authority model does not depend on transport.
The Canonical Registry is the only authoritative reference for the approved Prompt and its version lineage.

🧪 Pre-Claude Repair Audit — v4.0 → v4.1 Candidate
  Status
  Pre-Claude repair completed against the current v4.0 Candidate. v4.0 remains unchanged as historical baseline.
  Evidence Base
  - Current v4.0 prompt was read in full from the uploaded file.
  - Canonical Registry currently has no Approved Prompt.
  - Existing Version Registry already records v4.0 as Candidate and lists remaining gaps: frontier/stopping semantics, Entity Resolution discovery blind spot, runtime request mutation, price-decision policy, branch control, and freshness semantics.
  - External research was used to validate the repair directions, not to replace project-specific evidence.
  Repairs Applied in v4.1 Candidate
  1. Runtime scope lock
  User objective, constraints, price ceiling, target region, required attributes, and comparison basis are immutable for the run. Discoveries can create branches/hypotheses but cannot silently redefine the request.
  2. Run Contract and action-level auditability
  Each run now requires Run ID, prompt version, scope, evidence standard, complexity class, budget, coverage obligations, and known tool limits. Each Research Action must record its exact query/target, method, timestamp, branch, yield, retrieval status, affected objects, selection rationale, next-state effect, and budget debit.
  3. Evidence integrity
  Search snippets/previews/cached summaries are explicitly downgraded to lead/context unless the underlying source is unavailable. Material claims should rely on directly retrieved source content or structured first-party evidence whenever possible.
  4. Freshness semantics
  Freshness is separated from price-evidence strength. A directly observed price may be Freshness=Unknown without creating a semantic contradiction. Live transactional states can support Current when there is no material staleness signal; recent observation alone is not sufficient when archival/stale signals exist.
  5. Guarantee semantics
  “No Documented Guarantee” is now allowed only after the relevant accessible terms/offer documentation were actually reviewed. Retrieval failure or incomplete access yields Unknown.
  6. Transaction verification
  Performed-and-Evidenced now requires an actual authorized transaction/test with date, offer, amount, fees, outcome, and evidence. Reading a page never counts as transaction verification.
  7. Entity Resolution candidate-generation blind spot
  A Stage 0 candidate-generation layer was added. Blocking is explicitly a search-space reduction mechanism, not a non-match decision. High-value candidates without shared blocking signals remain eligible for deeper resolution.
  8. Coverage obligations
  The controller remains adaptive, but objective-driven coverage groups must be seeded so one highly productive discovery family cannot mask an unsearched materially relevant route. This is coverage protection, not equal-depth quota.
  9. Search strategy diversity
  Near-duplicate queries no longer count as meaningful exploration. Reformulation must change a material dimension such as terminology, role, channel, language, market, SKU, or seed.
  10. Search budget control
  Run complexity classes C1–C4 now have disclosed default action caps and a shared reserve. A hypothesis receives a minimum exploration floor when budget permits. A single branch is capped at 35% unless it is Critical for a live contradiction/headline claim.
  11. Stopping states
  Branch termination is now explicitly distinguished as Saturated, Retrieval-Limited, Budget-Limited, or Scope-Excluded. Retrieval and budget limits are never mislabeled as saturation.
  12. Exclusion handling
  Excluded entities are quarantined from commercial ranking and upstream inference but preserved in the research record, preventing loss of audit history and reducing false-positive damage.
  13. Effective acquisition cost
  Known mandatory taxes/charges are added explicitly; unknown mandatory components remain Unknown and never become zero.
  14. Output audit record
  Every run now ends with established facts, unresolved items, inaccessible routes, exclusions, counter-evidence survival, stopping rationale, unsearched material routes, potential conclusion-changing evidence, scope expansions, and tool limitations.
  Architectural Alternatives Reviewed
  - Monolithic v4.x with explicit control contracts and stronger state semantics.
  - Split Controller + Evidence Ledger architecture, with orchestration externalized from the research prompt.
  - Parallel specialist agents (discovery, verification, entity resolution, pricing) sharing a structured evidence graph.
  For the current  z.ai/Notion  setup, the first approach is the least disruptive; the second is the stronger longer-term architecture if external orchestration and persistent state become available. The third adds complexity and coordination cost and should be justified by measured workload, not assumed.
  External Research Signals
  DeepSearchQA explicitly evaluates multi-step research on systematic collation, deduplication/entity resolution, and stopping criteria, and reports persistent weaknesses in balancing recall and precision. BrowseComp similarly emphasizes persistence, strategic browsing, and synthesis across many sites. Current provenance work on LLM agents emphasizes claim-level evidence tracing and execution provenance rather than final-answer accuracy alone. Entity-resolution literature warns that early blocking can lose true matches, making blocking recall a real error surface. These findings support the v4.1 repair directions above.
