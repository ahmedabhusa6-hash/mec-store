# مرجع هندسة نظام الأتمتة المستمرة 24/7 — قالب قابل لإعادة الاستخدام
1. تعريف المرجع
هذا المستند هو  مرجع تأسيسي عام  لهندسة أنظمة الأتمتة التشغيلية المستمرة 24/7، وليس مرجعًا لمجال أعمال محدد.
الغرض منه هو إعادة استخدام نفس المنهج عند بدء أي مشروع جديد يحتاج إلى:
- تشغيل متكرر ومستمر.
- تنفيذ ذاتي أو شبه ذاتي.
- حالة تشغيلية مستديمة.
- طوابير أعمال.
- استئناف بعد الانقطاع.
- تحقق قبل اعتماد النتائج.
- تعافٍ من الأعطال.
- مراقبة تشغيلية.
- سجل تدقيق.
- تحديد للعمل التالي.
هذا المرجع لا يفترض نوع المشروع. يمكن تطبيقه على البحث، التشغيل، خدمة العملاء، المعالجة، التكاملات، الوكلاء، البيانات، المراقبة، المحتوى، العمليات التجارية، أو أي Workflow قابل للأتمتة.
2. الفكرة المركزية
النظام المطلوب ليس «بوتًا ينفذ أمرًا».
هو  Continuous Operations System :
نظام يبقى فعالًا تشغيليًا عبر دورات تنفيذ متتابعة، مع حفظ الحالة بين الدورات، وتحديد العمل التالي، والتعافي من الفشل، دون نهاية مقصودة.
النموذج:
TRIGGER → LOAD STATE → PLAN → EXECUTE → VALIDATE → COMMIT → PERSIST → NEXT WORK → NEXT TRIGGER
والتعافي:
FAILURE → CLASSIFY → PRESERVE STATE → RECOVER/RETRY/ESCALATE → VALIDATE → RESUME
3. تعريف 24/7
المعنى الصحيح
24/7 لا يعني أن عملية واحدة تبقى مفتوحة إلى الأبد.
المعنى الهندسي:
No Planned Termination
أي:
- لا يوجد تاريخ انتهاء مقصود للتشغيل.
- تنتهي كل دورة على حدة.
- تبقى الحالة محفوظة.
- يبدأ Trigger لاحق دورة جديدة.
- لا يتوقف النظام لمجرد انتهاء مهمة أو دورة أو عدم وجود عمل.
النموذج:
Cycle 1 → Persist → Cycle 2 → Persist → Cycle 3 → … → ∞
إذن:
Scheduled ≠ Live Continuous Process
بل:
Scheduled = Repeated Discrete Runs
4. الهدف المعماري
يجب أن يكون النظام:
Persistent + Resumable + Idempotent + Observable + Recoverable + State-Aware
أي:
- Persistent: حالته لا تعتمد على الذاكرة المؤقتة.
- Resumable: يستطيع الاستئناف.
- Idempotent: لا يسبب التكرار الضار.
- Observable: يمكن معرفة ما حدث.
- Recoverable: يستطيع التعافي من الأعطال.
- State-Aware: يعرف موقع كل عمل داخل دورة الحياة.

6. المكونات الأساسية
6.1 Trigger Engine
مسؤول عن بدء الدورات.
أنواع Trigger الممكنة:
- SCHEDULED
- EVENT
- MANUAL
- RETRY
- RECOVERY
- DEPENDENCY_COMPLETION
- QUEUE_AVAILABLE
- WATCHDOG
قاعدة:
لا توجد دورة بلا سبب تشغيل واضح يمكن تتبعه.
6.2 Orchestrator
يدير الدورة:
- تحميل الحالة.
- قراءة الطابور.
- تحديد العمل.
- ترتيب التنفيذ.
- التحكم في الاعتماديات.
- استدعاء التنفيذ.
- تشغيل التحقق.
- اعتماد التغيير.
- تحديد الخطوة التالية.
6.3 Persistent State
يحفظ:
- حالة النظام.
- حالة كل مهمة.
- حالة التنفيذ.
- نقاط الاستئناف.
- آخر نتيجة متحقق منها.
- التغييرات المعلقة.
- الأخطاء.
- الإعادات.
- العمل التالي.
- الاعتماديات.
6.4 Work Queue
كل عمل يجب أن يكون وحدة قابلة للتتبع.
الحد الأدنى:
- Task_ID
- Type
- Objective
- Priority
- Status
- Dependencies
- Input
- Expected_Output
- Validation_Rules
- Retry_Count
- Last_Attempt
- Checkpoint
- Next_Action
6.5 Planner
يحدد  ما الذي يمكن وينبغي تنفيذه الآن .
عوامل الاختيار:
- Priority
- Readiness
- Dependencies
- Deadline
- Impact
- Retry State
- Risk
- Resource Availability
6.6 Executor
ينفذ المهمة الفعلية.
يجب أن يكون التنفيذ:
- قابلًا للتجزئة.
- قابلًا للاستئناف.
- قابلًا للتتبع.
- غير مكرر ضارًا.
6.7 Validator
لا يكفي أن يرجع المنفذ SUCCESS.
التسلسل:
EXECUTE → VALIDATE → VERIFIED
6.8 Commit Layer
التغيير لا يصبح رسميًا إلا بعد:
PREPARE → WRITE → VERIFY → COMMIT CONFIRMED
6.9 Recovery Engine
مسؤول عن:
- تصنيف الفشل.
- حفظ آخر حالة صحيحة.
- إعادة المحاولة عند ملاءمتها.
- الاستئناف من Checkpoint.
- المصالحة عند وجود نتيجة مجهولة.
- التصعيد عند الحاجة.
6.10 Watchdog
لا ينفذ العمل الأساسي؛ يراقب صحة النظام.
يراقب:
- Last Heartbeat
- Last Successful Cycle
- Queue Stagnation
- Repeated Failures
- Long-running Jobs
- Dead Jobs
- Commit Failures
- Verification Failures
7. الفصل الإلزامي بين مستويات الحالة
لا تستخدم Status واحدًا لكل شيء.
System State
أمثلة:
- STARTING
- READY
- RUNNING
- DEGRADED
- RECOVERING
- PAUSED
- BLOCKED
- STOPPED
Cycle State
أمثلة:
- TRIGGERED
- INITIALIZING
- PLANNING
- EXECUTING
- VALIDATING
- COMMITTING
- COMPLETED
- PARTIAL
- BLOCKED
- FAILED
- RECOVERING
- NO_CHANGE
Task State
أمثلة:
- QUEUED
- READY
- RUNNING
- WAITING
- RETRYING
- COMPLETED
- FAILED
- BLOCKED
- CANCELLED
- DEAD_LETTER
8. الحالة ليست نتيجة واحدة
مثال تشغيلي صحيح:
System = RUNNING
Cycle = PARTIAL
Task A = COMPLETED
Task B = FAILED
Task C = BLOCKED
Task D = QUEUED
فشل مهمة واحدة لا يعني فشل النظام.
Task Failure ≠ System Failure

10. الاستمرارية
إذا كانت قائمة الأعمال فارغة:
Queue Empty → NO_WORK → Persist → Wait → Next Trigger
إذا لم يتغير شيء:
NO_CHANGE → Persist → Wait → Next Trigger
إذن:
NO_WORK ≠ STOP
NO_CHANGE ≠ STOP
11. الاستئناف Checkpointing
العملية الكبيرة يجب ألا تكون كتلة واحدة غير قابلة للاستئناف.
مثال:
Task
├── Step 1 ✓
├── Step 2 ✓
├── Step 3 ✓
├── Step 4 ✗
└── Step 5 -
عند الاستئناف:
Resume from Step 4
وليس إعادة العملية كاملة بلا سبب.
12. Idempotency
كل تنفيذ يحتاج إلى هوية قابلة للتتبع:
- Task_ID
- Execution_ID
- Attempt_ID
- Change_ID
- Cycle_ID
عند إعادة التشغيل:
Check Existing Execution
↓
Already Committed?
├── YES → DO NOT DUPLICATE
└── NO → RESUME / RETRY
13. نتيجة التنفيذ المجهولة
أخطر حالة ليست FAILED فقط، بل:
UNKNOWN
مثال:
- أرسل النظام طلبًا.
- انقطع الاتصال.
- لم نعرف هل نفذت العملية أم لا.
هنا:
UNKNOWN ≠ SAFE TO RETRY
القاعدة:
UNKNOWN → RECONCILE FIRST → THEN RETRY IF SAFE
لا تعاد العملية بشكل أعمى.
14. Commit Failure
عند فشل الكتابة:
FAILURE
↓
DO NOT CLAIM SUCCESS
↓
PRESERVE LAST VERIFIED STATE
↓
MARK PENDING CHANGE
↓
RECONCILE
↓
RETRY SAFELY
↓
VERIFY
مثال:
Last_Verified_State = ACTIVE
Pending_Change = NEW_STATE
Commit_Status = FAILED
ولا يصبح:
State = NEW_STATE
إلا بعد تحقق فعلي.
15. حالات Commit
- NOT_ATTEMPTED
- PREPARED
- COMMITTED
- VERIFIED
- FAILED
- RECONCILING
- RETRY_REQUIRED
قاعدة:
Commit Success ≠ Commit Verification
16. Dependency Management
إذا كانت:
A → B → C → D
وفشلت B:
A = COMPLETED
B = FAILED
C = BLOCKED
D = BLOCKED
لا يجوز تنفيذ C قبل إزالة سبب الاعتماد.
17. Human-in-the-Loop
الاستقلالية يجب أن تكون Policy-Controlled.
المستويات:
- AUTO_ALLOWED
- AUTO_WITH_VALIDATION
- HUMAN_APPROVAL_REQUIRED
- FORBIDDEN
المهام الحساسة لا تُنفذ تلقائيًا لمجرد أن Agent قادر عليها.
18. سجل التدقيق Audit Trail
يجب تسجيل الحد الأدنى:
- Event_ID
- Timestamp
- Actor
- Entity
- Previous_State
- New_State
- Action
- Result
- Correlation_ID
الهدف:
إعادة بناء ما حدث دون الاعتماد على الذاكرة الحوارية.
19. Observability
نظام 24/7 يحتاج إلى رؤية تشغيلية.
يجب أن يمكن الإجابة عن:
- ماذا حدث؟
- متى؟
- لماذا؟
- على أي مهمة؟
- ما الحالة السابقة؟
- ما الذي تغير؟
- هل تم التحقق؟
- ما الخطأ؟
- هل تمت الاستعادة؟
- ما العمل التالي؟

21. الفرق بين Automation وAgent وOrchestrator
Automation
ينفذ قاعدة أو إجراء محدد.
Agent
يمكنه اتخاذ قرارات وتنفيذ سلسلة أعمال أكثر مرونة.
Orchestrator
يدير تدفق النظام والاعتماديات والحالة.
Continuous Automation System
هو المنظومة الكاملة:
Automation + Agent + Orchestrator + State + Queue + Recovery + Validation + Observability
22. مكان الذكاء الاصطناعي

الذكاء الاصطناعي مكوّن داخل النظام وليس النظام كاملًا.

25. حالات الدورة الحرجة
COMPLETED
التنفيذ والالتزام والتحقق اكتملت.
PARTIAL
جزء موثوق اكتمل وجزء بقي مفتوحًا.
BLOCKED
تعذر الاستمرار بسبب قيد فعلي.
FAILED
فشلت الدورة على مستوى لا يمكن التعامل معه ضمن الدورة الحالية.
NO_CHANGE
لم يحدث تغير مادي.
NO_CHANGE لا يوقف النظام.

30. قواعد منع الأخطاء المعمارية
يحظر اعتماد النظام على:
- ذاكرة المحادثة.
- Context مؤقت.
- متغير محلي داخل عملية.
- نتيجة API غير متحقق منها.
- افتراض أن العملية لم تُنفذ لأن النتيجة لم تصل.
- إعادة التنفيذ دون فحص الهوية والحالة.
- إنشاء سجل جديد بدل تحديث سجل قائم دون سبب.
- اعتبار نجاح التنفيذ نجاحًا نهائيًا.
- اعتبار انتهاء دورة انتهاء النظام.
31. قانون الاستمرارية
القاعدة الحاكمة:
Cycle Completion ≠ System Completion
نهاية الدورة:
PERSIST STATE → WAIT FOR NEXT TRIGGER → START NEXT CYCLE
وليست:
COMPLETE → STOP

35. Anti-Patterns
1. Infinite Loop داخل جلسة واحدة
غير موثوق.
2. Schedule بلا State
ينتج دورات منفصلة غير مدركة للسياق.
3. AI Agent بلا Orchestration
يصعب استئنافه ومراقبته.
4. Retry بلا Idempotency
قد يكرر العمليات.
5. Commit بلا Verification
قد يعطي حالة خاطئة.
6. Failure = Stop
يقتل الاستمرارية.
7. Unknown = Retry
قد ينتج أثرًا مزدوجًا.
8. Queue واحدة بلا Dependency Model
تؤدي إلى تنفيذ غير صالح.
9. Logs بلا State
يعرف النظام ما حدث ولا يعرف أين يقف.
10. State بلا Audit
يصعب تفسير تغيراتها.
36. المبدأ الأهم
النظام الجيد لا يقاس فقط بقدرته على  تنفيذ العمل .
بل بقدرته على:
KNOW → DECIDE → EXECUTE → VERIFY → REMEMBER → RECOVER → RESUME
أي:
يعرف حالته، يقرر العمل، ينفذه، يتحقق منه، يحفظ ما حدث، يتعافى من الفشل، ثم يستأنف.
37. قاعدة التسمية المهمة
لا تستخدم تعبيرات فضفاضة مثل:
- «شغال دائمًا».
- «لا يتوقف».
- «ذكاء يعمل 24 ساعة».
استخدم وصفًا هندسيًا:
Persistent recurring automation with stateful execution, recovery, and next-work scheduling.
وإذا كان النظام قائمًا على دورات مجدولة:
Continuous operation through repeated discrete execution cycles.
38. الخلاصة التشغيلية
النظام المطلوب هو  محرك عمليات مستمرة  وليس مجرد Automation Script أو Bot.
جوهره:
Trigger
→ State
→ Queue
→ Plan
→ Execute
→ Validate
→ Commit
→ Persist
→ Observe
→ Recover
→ Determine Next Work
→ Next Trigger
→ …
والاستمرارية لا تأتي من بقاء جلسة مفتوحة، بل من  استدامة الحالة واستمرار Trigger واستقلال الدورات وقابلية الاستئناف والتعافي.
39. الخلاصة الشاملة القابلة لإعادة الاستخدام
عند بدء مشروع جديد، لا تبدأ بالسؤال:
«ما الأداة التي ستنفذ المهمة؟»
ابدأ بالأسئلة:
- ما العملية التي يجب أن تستمر؟
- ما وحدة العمل؟
- ما Trigger؟
- ما الحالة التي يجب حفظها؟
- كيف نحدد العمل التالي؟
- كيف ننفذ؟
- كيف نتحقق؟
- كيف نعتمد التغيير؟
- ماذا يحدث عند الفشل؟
- كيف نعرف هل التنفيذ الأول حدث أم لا؟
- كيف نستأنف بعد الانقطاع؟
- كيف نمنع التكرار؟
- كيف نراقب النظام؟
- متى نحتاج إنسانًا؟
- ما الذي يبقى محفوظًا بعد انتهاء الدورة؟
إذا كانت هذه الأسئلة محسومة، يمكن بناء نظام 24/7 قابل للتوسع بصورة صحيحة.
40. القواعد غير القابلة للتفاوض
Persistent State > Context Memory
Validated State > Unverified Result
Execution ≠ Validation
Validation ≠ Commit
Commit ≠ Verification
Unknown ≠ Safe Retry
Task Failure ≠ System Failure
NO_WORK ≠ STOP
NO_CHANGE ≠ STOP
Cycle Completion ≠ System Completion
Scheduled ≠ Live Process
Idempotency is mandatory for retryable actions
Recovery must preserve the last verified state
No claim of execution without verified execution
The system continues by state persistence + next trigger, not by one immortal process
41. استخدام هذا المرجع عند مشروع جديد
عند بدء مشروع جديد، يُنشأ  Project Operations Specification  منفصل، ثم يحدد:
PROJECT → WORK UNITS → TRIGGERS → STATES → QUEUE → EXECUTION → VALIDATION → COMMIT → RECOVERY → OBSERVABILITY → CONTINUITY
ولا تُنسخ كل التفاصيل آليًا إلى المشروع؛ يتم أخذ ما ينطبق فقط مع الحفاظ على المبادئ الحاكمة.

43. Hardening Review — 2026-09-26
أظهرت المراجعة المعمارية أن المواصفة الأساسية كانت قوية في State / Validation / Commit / Recovery، لكنها تحتاج إلى طبقة Reliability & Distributed-Execution أكثر صراحة.
الفجوات التي تم اعتماد إصلاحها في المواصفة
43.1 منع تداخل الدورات
لا يُفترض أن الجدولة تمنع تشغيل دورتين على نفس العمل في الوقت نفسه.
يجب استخدام  lock / lease / execution ownership  أو آلية مكافئة قبل Claim العمل.
43.2 Retry Budget
لا يكفي تحديد عدد محاولات لكل مهمة فقط؛ يجب أن توجد  ميزانية إعادة محاولة مجمعة  لحماية النظام والاعتماديات من Retry Storm.
43.3 Exponential Backoff + Jitter
إعادة المحاولة تكون مع Backoff مناسب، ويُفضّل وجود عشوائية زمنية عند التوازي لتقليل thundering herd.
43.4 Circuit Breaker
عند استمرار فشل dependency، لا تستمر المهام في ضربها. افتح Circuit مؤقتًا، ثم اختبر الاستعادة قبل إعادة المرور الطبيعي.
43.5 Dead-Letter / Poison Job Isolation
المهمة التي تفشل بشكل دائم لا يجوز أن تدور إلى الأبد في الطابور الرئيسي.
بعد شروط محددة تنقل إلى  Dead-Letter / Quarantine  مع الحفاظ على سجلها وإمكانية إعادة إدخالها بعد الإصلاح.
43.6 Backpressure + Queue Durability
عند ارتفاع معدل المنتجين فوق قدرة المستهلكين، يجب أن يصبح Queue جزءًا من التحكم في الحمل، مع مراقبة Queue Depth / Queue Age واتخاذ قرار بالتوسعة أو تأخير أو إسقاط العمل غير الحرج بحسب السياسة.
43.7 At-Least-Once كافتراض افتراضي
لا يُفترض Exactly-Once على مستوى النظام كاملًا. يجب أن تكون عمليات الاستهلاك idempotent، ويجب تتبع Message/Execution IDs لمنع الأثر المزدوج.
43.8 Visibility / Lease Timeout
العمل المأخوذ من Queue يحتاج إلى مهلة ownership قابلة للتجديد عند العمليات الطويلة حتى لا يستلم عامل ثانٍ المهمة قبل انتهاء الأول، مع بقاء الحاجة إلى idempotency.
43.9 Priority Fairness / Starvation
الأولوية العالية قد تمنع الأعمال الأقل أولوية من الوصول إلى التنفيذ. يجب دعم سياسة Fairness/Aging عندما يتطلب المشروع ذلك.
43.10 Dual-Write Protection
إذا احتاجت العملية إلى تحديث حالة دائمة وإرسال رسالة/حدث، يجب فحص  dual-write risk  واستخدام Transactional Outbox أو آلية تحقق مكافئة عندما ينطبق النمط.
43.11 Durable Execution / Checkpointed Progress
الأعمال الطويلة ينبغي تصميمها كخطوات قابلة للاستئناف مع حفظ تقدم durable، بدل الاعتماد على ذاكرة العامل.
43.12 Observability موحدة
يجب ربط Logs + Metrics + Traces بسياق تنفيذ مشترك مثل Execution_ID / Correlation_ID، بحيث يمكن تتبع رحلة العملية عبر المكونات.
43.13 SLO / Alert Quality
المراقبة ليست مجرد جمع Logs؛ يجب تحديد إشارات صحة ذات معنى، وألا ينتج النظام Alerts غير قابلة للفعل أو ضوضاء تؤدي إلى Alert Fatigue.
43.14 حدود الاستقلالية
يجب تعريف ما يمكن إصلاحه تلقائيًا، وما يحتاج موافقة بشرية، وما يجب منعه. لا يكفي أن تكون الأداة قادرة على التنفيذ.

Canonical Execution Directive — 2026-09-26
نفّذ دورة واحدة من منظومة الأتمتة المركزية 24/7. النطاق: المنظومة نفسها فقط.
TRIGGER → LOAD VERIFIED STATE → PRE-FLIGHT → OVERLAP/OWNERSHIP CHECK → IDENTIFY GAP → RESEARCH/COMPARE ALTERNATIVES → VALIDATE → DESIGN FIX → SIDE-EFFECT CHECK → APPLY SAFE FIX → VERIFY → PERSIST → QC → DETECT NEW GAPS → PRIORITIZE → NEXT TRIGGER
القواعد: لا ادعاء بلا تنفيذ متحقق؛  SPECIFICATION_FIXED ≠ IMPLEMENTED_VERIFIED ≠ BLOCKED ؛  UNKNOWN → RECONCILE FIRST ؛ لا Retry بلا حدود؛ افترض  at-least-once  ما لم يثبت غير ذلك؛ احمِ الآثار الجانبية بـidempotency؛ لا تتجاوز Billing/Permissions؛ لا تخلط Runtime المركزي مع مشاريع قائمة.
في كل دورة: افحص الفجوات، ابحث عن بدائل حتى بعد العثور على حل، طبّق الإصلاح غير المدمّر عندما تدعمه الأدوات فعليًا، ثم سجّل الدليل والحالة وBlockers وNext Work في Notion.
معيار إضافي — البحث عن بدائل تشغيل بلا اشتراك مدفوع
عند وجود عائق Billing أو طلب صريح لتجنب الاشتراكات، يجب أن تبحث كل دورة عن منصات بديلة لـRender وغيرها، مع تصنيف دقيق:
- $0/month:  خطة مجانية بلا رسم شهري.
- Free Tier محدود:  مجانية ضمن حدود تشغيلية واضحة.
- Trial/Credit:  مجانية مؤقتة أو قائمة على رصيد تجريبي.
- Paid:  تتطلب اشتراكًا/دفعًا للاستخدام المطلوب.
لا يكفي إثبات السعر؛ يجب التحقق من ملاءمة المنصة لمتطلبات Central Runtime: scheduling، background workers، queue، durable state، persistence، retries، ownership/lease، recovery، observability، execution limits، sleep/scale-to-zero، وrepository isolation.
