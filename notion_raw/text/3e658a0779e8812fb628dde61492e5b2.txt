Unified Continuous Knowledge Operation — Operating Contract
Trigger model:  USER-TRIGGERED / SCHEDULED / EVENT / RESUME بحسب المتاح فعليًا. لا يُدّعى تشغيل مستمر بلا Trigger.
Core loop:  Knowledge State → Discovery → Triage → Research → Validation → Conflict Check → Synthesis → Knowledge Commit → Quality Control → Gap Detection → Priority Queue → Next Trigger.
Critical separation:  Knowledge State ≠ Change Type ≠ Conflict Status.
Knowledge State:  DISCOVERED · TRIAGED · RESEARCHING · VALIDATING · SYNTHESIZED · ACTIVE · CONTESTED · CONFLICTED · INSUFFICIENT_EVIDENCE · DUPLICATE · OUTDATED · SUPERSEDED · REJECTED
Change Type:  CREATED · CONFIRMED · UPDATED · CORRECTED · CONTEXTUALIZED · DUPLICATED · SUPERSEDED · REJECTED
Conflict Status:  NONE · OPEN · RESOLVED · PARTIALLY_RESOLVED
Cycle completion rule:  لا تنتهي الدورة عند كتابة التقرير؛ تنتهي فقط بعد تحديث الحالة المعرفية، تسجيل ما تغير، تسجيل ما لم يُحسم، اكتشاف الفجوات، وتحديد العمل التالي.
Persistence rule:  كل دورة تبدأ من آخر حالة مؤكدة وتنتهي بحالة أحدث قابلة للاستئناف. عند عدم وجود تغيير معرفي حقيقي يُسجل NO_CHANGE. عند تعذر التنفيذ يسجل BLOCKED.
24/7 operational truth:  الاستمرارية هنا هي استمرارية الحالة والعمل التالي عبر Runs منفصلة.  لا توجد حاليًا جدولة Deep Marketing فعّالة متحقق منها ؛ وجود نموذج التشغيل أو سجل الدورات لا يساوي وجود Trigger فعّال.

  1. نطاق العمل
  هذه الصفحة هي سجل مرجعي تحليلي للمحادثة الحالية الخاصة بمنظومة  Deep Marketing — Continuous Knowledge Operation  وما نتج عنها من قرارات وحالات وأدلة وتسويات تشغيلية.
  حدود النطاق:  لا تُضاف موضوعات خارج منظومة Deep Marketing/KOS إلا إذا كانت ضرورية مباشرة للتحقق من حالة أو قرار داخلها. المصادر الخارجية تستخدم للتحقق والسد المحدود للفجوات، ولا تغيّر نطاق العمل.
  2. الهدف التشغيلي المستخلص
  تحويل البحث التسويقي من تجميع معلومات إلى  Knowledge Operating System  يحافظ على:
  - الأدلة ومصدرها.
  - الادعاءات وحدودها.
  - الفصل بين Fact / Evidence / Interpretation / Hypothesis / Inference / Recommendation.
  - حالة المعرفة وتاريخ تغيرها.
  - السياق والمستوى والمنهج والنتيجة.
  - provenance من المصدر إلى المعرفة والتغيير.
  - فجوات قابلة للتحويل إلى Research Queue.
  - استمرارية قائمة على الحالة المحفوظة، لا على محادثة حية دائمة.
  3. النموذج الحاكم
  Knowledge State → Discovery → Triage → Research → Validation → Conflict Check → Synthesis → Knowledge Commit → Quality Control → Gap Detection → Priority Queue → Persist State → Next Trigger.
  النظام المجدول عبارة عن دورات منفصلة؛ الاستمرارية المقصودة هي استمرارية  الحالة + العمل التالي  وليست عملية Live 24/7 داخل النموذج.
  4. القواعد التشغيلية المستخلصة
  - لا ادعاء نهائيًا بلا تنفيذ/تحقق موثوق.
  - لا Knowledge Commit بلا Evidence.
  - لا تغيير نهائي في الحالة بلا Verified Persistence.
  - Research ≠ Source ≠ Evidence ≠ Knowledge Asset.
  - Search Result ≠ Knowledge Commit.
  - Knowledge State ≠ Change Type ≠ Conflict Status ≠ Commit Status.
  - SUPERSEDED ≠ DELETED.
  - عند UNKNOWN: RECONCILE FIRST.
  - عند فشل Commit: حفظ آخر حالة موثقة، تسجيل التغيير المعلّق، ثم reconciliation/retry/verify.
  - لا ترفع مثالًا واحدًا إلى Pattern عام دون تكرار مناسب.
  - لا تحول Pattern إلى Principle تلقائيًا.
  - لا تساوي كثرة الأدلة من الجهة نفسها مع استقلالية الأدلة.
  - يجب حفظ المستوى والسياق والشروط والقيود مع كل ادعاء مهم.
  - قوة الدليل تُسند إلى  link/outcome/design  وليس إلى mechanism chain ككتلة واحدة.
  - لا ACTIVE promotion للمعرفة المركبة لمجرد اكتمال بنيتها؛ الترقية تكون على مستوى الادعاء وبنطاقه وبشروط الأدلة والنقل.

  6. القرارات المحسومة
  6.1 فصل قوة الدليل
  تم تثبيت قاعدة أن قوة الدليل تختلف حسب الرابط والنتيجة وتصميم الدراسة. هذه القاعدة موثقة في CHG-RSH2-010 وDER-RSH2-010.
  6.2 معايرة RSH-16
  الادعاء القابل للاستخدام ليس «السعر يرفع المبيعات» بصورة عامة. الأدلة تدعم بصورة أضيق آثارًا على التقييم/القيمة ومسارًا bounded من anchoring إلى expected-price latitude ثم purchase intention، مع بقاء realized sales/profit غير مثبتين على نحو عام.
  6.3 معايرة RSH-17
  تجربة eBay العشوائية تدعم أثر الوصول إلى analytics dashboard على الإيرادات/المبيعات في سياق eBay SMEs، مع دور مهم للمراقبة النشطة للأداء. كما أن دراسة UK retail SMEs المنشورة في 2026 توفر دعمًا تجريبيًا مباشرًا لرابط BDAC → market agility، بينما لا تزال market agility → firm performance والوساطة الكاملة بحاجة إلى دليل سببي مستقل. لذلك لا يجوز اختزال السلسلة في Claim سببي عام واحد.
  6.4 Stage Gate
  المعمارية الكلية KNG-43 بقيت SYNTHESIZED؛ لا توجد ترقية شاملة إلى ACTIVE.
  6.5 Claim-Level Evidence Register
  أصبح مستوى الادعاء هو وحدة التقييم المناسبة بدل تقييم architecture ككتلة واحدة.
