مشروع بيع الخدمات الرقمية عبر Telegram — Payment Architecture & ProdSeller
========================================
Store Brand
Proposed name: وصلة رقمية — Wasla Digital
Brand decision status: Working brand candidate; visual identity direction in development; final naming/trademark/domain/Telegram-handle decision pending.
Positioning direction: A digital-services storefront delivered through Telegram, with local Yemeni payment collection and ProdSeller used as a downstream supplier. The brand should remain independent of any single supplier or product category.
New Review Scope — Supplier PDF + Store Architecture
The uploaded supplier PDF is evidence for the current ProdSeller store/product model only. Image-based information must be treated as a point-in-time snapshot and not as a permanent catalog, price list, or inventory guarantee. The system must retrieve current supplier data where the API supports it.
Supplier-side risks to verify before publication
Product type must be classified before sale: key, activation link, invitation/admin, account/access credential, educational/eligibility product, subscription, or other delivery mode.
Supplier availability does not by itself prove that resale is permitted by the original service provider.
Products with account credentials, full access, invitations, or educational eligibility require product-specific Terms/ToS and fulfillment-risk review before listing.
Supplier stock and price may change; the storefront must not hard-code historical values as authoritative.
Fulfillment behavior varies by product; the order engine must support multiple delivery models instead of assuming every product returns a simple text key.
Canonical storefront flow
Customer → Telegram storefront → product eligibility check → current price/stock check → order creation → YER payment → payment verification → idempotency gate → ProdSeller API → fulfillment adapter → customer delivery → audit/warranty state.

Current Critical Questions
Which Yemeni payment provider can legally and technically serve this project as an individual operator?
Can the provider issue a merchant capability/API or reliable transaction-status mechanism without a Commercial Register?
Which ProdSeller products are suitable for resale and which should be excluded?
Which fulfillment modes can be automated safely through the ProdSeller API?
What warranty/refund rules apply per product type?
How will ambiguous payment and supplier responses be reconciled without duplicate fulfillment?
Decision Rule
Do not build or publish the complete catalog until payment eligibility, product resale eligibility, and fulfillment behavior have been verified to the level required for each product.

Canonical Bilingual Project Brief
English — Canonical Project Definition
Strategic Objective
Build a Telegram-based digital commerce system for customers in Yemen. Telegram is the customer interface; a Yemeni payment provider is the local collection layer in Yemeni Rial (YER); ProdSeller is the downstream supplier accessed through its API.
The customer must not be required to use Binance, USDT, or ProdSeller directly.
Core Financial Separation
Two financial flows must remain logically and operationally separate:
Customer collection: Customer → Yemeni payment provider → merchant balance.
Supplier settlement: Operator working capital → approved settlement method → ProdSeller balance.
Supplier settlement must never be treated as the customer payment gateway.
Canonical Order Flow
Telegram Bot → Product Catalog → Pricing Engine → Order Creation → Local Payment Request → Payment Verification → Idempotency Gate → ProdSeller API → Supplier Result → Delivery to Telegram → Audit Record.
Payment Provider Selection Rule
Do not choose a provider because it is popular or has a merchant application. The provider is eligible only if the required merchant capability is contractually/technically available for this project.
Minimum acceptable capability:
Merchant account appropriate for the activity.
Payment API, or a reliable Transaction Inquiry / Status API.
A way to bind payment to a unique order/reference.
Verifiable payment state.
Support for YER.
Permission to operate the intended digital-service activity.
Webhook/Callback is preferred but not mandatory if reliable transaction-status polling is available.
Critical Regulatory/Eligibility Question
Do not assume that a personal wallet can be used for commercial collection, and do not assume that an API can be obtained without a Commercial Register.
The project must separately verify:
Personal wallet eligibility.
Merchant account eligibility.
Payment gateway eligibility.
API access eligibility.
Commercial Register requirement.
KYC requirements.
Digital-services / resale restrictions.
A provider is considered UNVERIFIED until the relevant requirement is supported by authoritative evidence.
Failure-Safe Order State Model
The implementation must explicitly handle:
duplicate payment;
duplicate webhook/callback;
late payment;
wrong payment amount;
unknown transaction;
payment confirmed while supplier order fails;
supplier order succeeds while Telegram delivery fails;
payment-provider timeout;
supplier timeout;
retry after an ambiguous response;
concurrent requests for the same order.
Every state transition must be deterministic, auditable, and idempotent.
Supplier Integration
ProdSeller is an external supplier, not the customer-facing system.
The integration must protect the ProdSeller API key, prevent duplicate supplier orders, record supplier order identifiers, and reconcile supplier state with the internal order state.
Pricing
Customer price must be derived from actual economics:
Supplier Cost + Payment Fees + Settlement/FX Cost + Risk Reserve + Profit = Customer Price.
Supplier prices and inventory may change; the system must not assume that a previously observed price or stock level remains valid.
MVP Strategy
Start with one eligible payment provider, one Telegram bot, one validated payment flow, and the ProdSeller integration. Add a second payment provider only after the first path is proven.
The payment layer must be implemented behind an abstraction so the provider can later be replaced without rewriting the order engine or ProdSeller integration.
Evidence Standard
Classify every material statement as one of:
PROVEN — supported by direct evidence.
PARTIALLY PROVEN — some required evidence exists, but not all.
UNVERIFIED — insufficient authoritative evidence.
CONTRADICTED — reliable sources disagree.
BLOCKED — cannot be resolved without an external dependency.
Notion describes intent, decisions, assumptions, and history. The running code, tests, Git history, and runtime evidence establish implementation reality. Neither source should automatically override the other.
Immediate Decision Gate
Do not build the final automated payment path until the first candidate provider confirms, preferably in writing, that the project can legally/contractually use the required merchant capability and technical verification mechanism.
العربية — التعريف المرجعي للمشروع
الهدف الاستراتيجي
بناء نظام تجارة رقمية عبر Telegram موجه للعملاء في اليمن؛ يكون Telegram واجهة العميل، ويكون مزود دفع يمني طبقة التحصيل بالريال اليمني، بينما يكون ProdSeller موردًا خلفيًا يتم الوصول إليه عبر API.
لا ينبغي أن يُطلب من العميل النهائي استخدام Binance أو USDT أو التعامل المباشر مع ProdSeller.
الفصل المالي الأساسي
يجب الفصل منطقيًا وتشغيليًا بين مسارين ماليين:
تحصيل العميل: العميل → مزود الدفع اليمني → رصيد التاجر.
تسوية المورد: رأس المال التشغيلي → وسيلة التسوية المعتمدة → رصيد ProdSeller.
لا يجوز اعتبار تسوية رصيد ProdSeller بوابة دفع للعميل.
التدفق المرجعي للطلب
Telegram Bot → كتالوج المنتجات → محرك التسعير → إنشاء الطلب → طلب الدفع المحلي → التحقق من الدفع → بوابة منع التكرار → ProdSeller API → نتيجة المورد → تسليم المنتج عبر Telegram → سجل تدقيق.
قاعدة اختيار مزود الدفع
لا يتم اختيار المحفظة بسبب الشهرة أو لمجرد امتلاكها تطبيقًا للتاجر. يكون المزود مؤهلًا فقط عندما تكون القدرات المطلوبة متاحة لهذا المشروع تعاقديًا وتقنيًا.
الحد الأدنى المطلوب:
حساب تاجر مناسب لطبيعة النشاط.
Payment API أو Transaction Inquiry / Status API موثوق.
وسيلة لربط عملية الدفع بطلب أو مرجع فريد.
إمكانية إثبات حالة الدفع.
دعم الريال اليمني.
السماح بنشاط بيع الخدمات الرقمية المقصود.
الـWebhook/Callback مفضل، لكنه ليس شرطًا مطلقًا إذا كان الاستعلام الموثوق عن حالة العملية متاحًا.
السؤال التنظيمي الحاسم
لا يُفترض أن المحفظة الشخصية تسمح بالتحصيل التجاري، ولا يُفترض أن الحصول على API ممكن بدون سجل تجاري.
يجب التحقق بصورة منفصلة من:
أهلية المحفظة الشخصية.
أهلية حساب التاجر.
أهلية بوابة الدفع.
أهلية الوصول إلى API.
شرط السجل التجاري.
متطلبات KYC.
قيود بيع الخدمات الرقمية وإعادة البيع.
لا يُعتبر أي ادعاء مثبتًا حتى تدعمه جهة موثوقة أو دليل مباشر.
نموذج الحالات الآمن للطلب
يجب أن يتعامل النظام صراحةً مع:
الدفع المكرر.
تكرار Webhook/Callback.
الدفع المتأخر.
دفع مبلغ خاطئ.
معاملة غير معروفة.
تأكيد الدفع مع فشل إنشاء طلب المورد.
نجاح طلب المورد مع فشل التسليم عبر Telegram.
انتهاء مهلة مزود الدفع.
انتهاء مهلة المورد.
إعادة المحاولة بعد استجابة غامضة.
الطلبات المتزامنة على نفس العملية.
كل انتقال للحالة يجب أن يكون حتميًا وقابلًا للتدقيق ومحصنًا ضد التكرار.
تكامل المورد
ProdSeller مورد خارجي وليس واجهة العميل.
يجب حماية مفتاح API، ومنع تنفيذ الطلب لدى المورد مرتين، وحفظ معرف طلب المورد، وتحقيق المطابقة بين حالة المورد والحالة الداخلية للطلب.
التسعير
سعر العميل يجب أن ينتج من الاقتصاد الفعلي للعملية:
تكلفة المورد + رسوم الدفع + تكلفة/فرق التسوية والصرف + احتياطي المخاطر + الربح = سعر العميل.
أسعار ومخزون ProdSeller قابلة للتغير، لذلك لا يجوز افتراض ثبات السعر أو المخزون الذي تمت رؤيته سابقًا.
استراتيجية MVP
ابدأ بمزود دفع واحد مؤهل، وبوت Telegram واحد، وتدفق دفع واحد تم التحقق منه، وتكامل ProdSeller. لا تضف مزودًا ثانيًا إلا بعد إثبات المسار الأول.
يجب وضع طبقة الدفع خلف abstraction حتى يمكن استبدال المزود لاحقًا دون إعادة كتابة Order Engine أو تكامل ProdSeller.
معيار الأدلة
يجب تصنيف كل معلومة جوهرية إلى إحدى الحالات التالية:
PROVEN / مثبت — توجد أدلة مباشرة.
PARTIALLY PROVEN / مثبت جزئيًا — توجد بعض الأدلة لكن المتطلبات لم تثبت كلها.
UNVERIFIED / غير مثبت — الأدلة الموثوقة غير كافية.
CONTRADICTED / متعارض — توجد مصادر موثوقة متعارضة.
BLOCKED / متعطل — لا يمكن حسمها دون اعتماد خارجي.
Notion يوثق النية والقرارات والافتراضات والتاريخ، بينما الكود الفعلي والاختبارات وGit وأدلة التشغيل تثبت واقع التنفيذ. لا يجوز افتراض أن أحد المصدرين يلغي الآخر تلقائيًا.
بوابة القرار الفورية
لا يبدأ بناء مسار الدفع الآلي النهائي قبل أن يؤكد أول مزود مرشح، ويفضل كتابيًا، أن المشروع يستطيع استخدام القدرة التجارية المطلوبة وآلية التحقق التقنية بصورة نظامية ومناسبة.
الغرض
بناء مشروع فردي لبيع خدمات ومنتجات رقمية عبر Telegram في اليمن، بحيث يكون Telegram Bot هو واجهة العميل، وتكون خدمات الدفع اليمنية طبقة تحصيل بالريال اليمني، بينما يكون ProdSeller موردًا خلفيًا يتم الوصول إليه عبر API لتنفيذ الطلبات.
1. الفكرة الصحيحة
المشروع ليس «بوتًا مربوطًا بمحفظة» فقط، بل نظام تجارة رقمي بطبقتين منفصلتين:
طبقة العميل والتحصيل
Telegram Bot → اختيار المنتج → إنشاء Order → تحديد السعر بالريال اليمني → الدفع المحلي → إثبات/تحقق الدفع → اعتماد الطلب.
طبقة المورد والتسوية
Order Approved → ProdSeller API → استلام نتيجة المورد → تسليم المنتج للعميل.
تمويل رصيد ProdSeller منفصل عن تحصيل العملاء. الطرق التي يوفرها المورد حاليًا هي Binance Pay وCryptoBot باستخدام USDT وUSDT BEP20. لا ينبغي جعل العميل النهائي يتعامل مع هذه الطبقات.

3. المبدأ الحاكم للدفع
لا يجب اختيار المحفظة لمجرد أنها مشهورة أو تملك تطبيق تاجر. الشرط الحاسم هو أن تستطيع الخدمة دعم أحد مسارين موثوقين:
Webhook / Callback عند نجاح الدفع.
Transaction Inquiry / Status API يسمح للنظام بالاستعلام عن حالة عملية دفع مرتبطة بـOrder ID فريد.
وجود Webhook أفضل، لكنه ليس شرطًا مطلقًا في المرحلة الأولى. Polling الموثوق يمكن أن يكون بديلًا عمليًا.
4. مشكلة السجل التجاري
عدم امتلاك سجل تجاري ليس استنتاجًا بأنه لا يمكن تشغيل المشروع. يجب الفصل بين:
فتح محفظة شخصية.
فتح حساب تاجر.
تفعيل Payment Gateway.
الحصول على Merchant API.
السماح للفرد ببيع خدمات رقمية.
حتى الآن يجب التعامل مع «هل يقبل مزود معين فردًا بلا سجل تجاري للحصول على Merchant API؟» باعتبارها نقطة تحقق خارجية يجب إثباتها كتابيًا من المزود، وليس افتراضًا عامًا.

10. التسعير
السعر النهائي ليس supplier_price فقط. يجب احتساب:
تكلفة المورد.
رسوم الدفع المحلي.
فرق سعر الصرف.
احتياطي المرتجعات/الفشل.
هامش الربح.
صيغة أولية:
سعر البيع = تكلفة المورد + تكلفة الدفع + تكلفة/هامش التحويل + احتياطي المخاطر + الربح.
11. نقاط الفشل الواقعية
مزود الدفع قد يقبل الأفراد كمستخدمين لكنه لا يمنحهم Merchant API.
وجود API لا يعني وجود Webhook.
وجود Webhook لا يعني أنه موثوق أو قابل للاعتماد دون تحقق إضافي.
QR أو التحويل اليدوي قد يكون مناسبًا للـMVP لكنه لا يكفي كدليل دفع آلي بمفرده.
أسعار ProdSeller والمخزون تتغير؛ لا ينبغي تخزين سعر ثابت دون آلية مزامنة.
المورد قد يسلم الطلب بعد تأخير أو يعيد حالة فشل؛ Order Engine يجب أن يكون قابلًا لإعادة المحاولة بأمان.
بعض الخدمات الرقمية قد تكون لها شروط استخدام أو قيود إعادة بيع؛ يجب فحص شروط المورد والمنتج قبل تشغيله تجاريًا.
التعامل مع أموال العملاء قد يفرض متطلبات تنظيمية لا يحسمها مجرد امتلاك محفظة شخصية.
P2P/USDT طبقة تسوية وليس بوابة دفع العميل.
API Keys والأسرار يجب ألا تدخل Notion أو الرسائل أو Git.
12. استراتيجية التنفيذ
المرحلة 0 — تحقق الجدوى:
احصل على إجابة مباشرة من 3–4 مزودي الدفع عن Merchant API + Inquiry/Webhook + قبول الفرد بلا سجل تجاري + بيع الخدمات الرقمية.
المرحلة 1 — MVP:
محفظة واحدة + Telegram Bot + تحقق دفع واحد + ProdSeller API + تسجيل الطلبات.
المرحلة 2 — أتمتة:
Webhook إن توفر، وإلا Polling موثوق، مع Idempotency وRetries وAudit Logs.
المرحلة 3 — التوسع:
إضافة مزود دفع احتياطي وإدارة أسعار ومخزون ProdSeller مركزيًا.
13. السؤال الحاسم الذي يجب أن يجيب عنه البحث الخارجي
«ما أفضل مزود دفع في اليمن لشخص/مشروع صغير لا يملك سجلًا تجاريًا، ويحتاج استقبال YER من عملاء Telegram ثم التحقق البرمجي من الدفع وتنفيذ الطلب عبر ProdSeller API؟»

Trademark/name availability in the target market.

Whether the Arabic/English pairing should be وصلة رقمية | Wasla Digital or a different English rendering.

Brand Identity — Working Direction — 2026-09-21
Brand Concept
Wasla Digital / وصلة رقمية is positioned around the core idea of connection: connecting the customer in Yemen to a digital product or service through a controlled commerce layer. The identity should communicate connection, trust, digital utility, simplicity, and scalability without being tied to ProdSeller or any single product category.
Logo Concept
The current concept uses two interconnected forms with a central gold element.
The two forms represent two sides of the transaction: customer-side interaction and service-side fulfillment.
The central element represents the connection or completion point.
The visual language may suggest continuity and flow, but these are secondary interpretations rather than requirements.
The final mark must be distinctive enough to avoid looking like a generic chain or infinity symbol.
Differentiation should come primarily from silhouette, negative space, proportions, interlock logic, and the central accent rather than added detail.
Color Direction
Primary Deep Teal: #063B38
Secondary Teal: #0B6B5E
Light Teal Accent: #35B89A
Gold Accent: #C9A34E
Off White: #F5F7F6
Near Black: #07110F
Usage rule:
Deep Teal = primary brand foundation and dark UI surfaces.
Teal = secondary brand elements.
Light Teal = limited digital highlights.
Gold = focal/value accent; do not allow it to dominate the system.
Off White and Near Black = primary light/dark interface neutrals.
Visual Direction
The identity should be modern, digital, professional, calm, and scalable.
Avoid positioning the brand as a luxury-fashion identity, a generic technology startup, or a loud discount store.
Required Logo System
The final identity work must validate:
Primary logo.
Horizontal lockup.
Stacked lockup.
App icon.
Telegram avatar.
Favicon.
Light-background version.
Dark-background version.
One-color black version.
One-color white version.
Small-size reproduction.
Presentation Format
The brand-identity presentation should use a 16:9 canvas and show the logo, Arabic and English name, color palette with HEX values, light/dark variants, monochrome variants, app/Telegram icon applications, and a limited set of practical digital mockups.
Current Status
CONCEPT — NOT FINAL.
The current direction is approved for further design development, not for final brand adoption. Final adoption remains dependent on logo distinctiveness testing and availability checks for the name, domain, Telegram handle, and relevant trademark/name collisions.
